## 一、核心发现：MessageList 是弹幕系统的核心协议

### 1.1 protobuf 消息结构（代码级确认）

```go
// serverMsg.pb.go - 已生成的 protobuf 代码
type MessageList struct {
    Type      string     `protobuf:"bytes,1,opt,name=type,proto3"`  // "ChatMessage" | "GiftMessage" | "LikeMessage"
    MsgList   []*Message `protobuf:"bytes,2,rep,name=msgList"`
    AccountId string     `protobuf:"bytes,3,opt,name=AccountId"`
    RoomId    string     `protobuf:"bytes,4,opt,name=RoomId"`
}

type Message struct {
    Type      string  // 消息类型（礼物/评论/点赞）
    Name      string  // 用户昵称
    Uid       string  // 用户openId
    HeadImg   string  // 头像URL
    Content   string  // 评论内容（ChatMessage）
    Count     string  // 点赞数（LikeMessage）
    Total     string  // 礼物总价（GiftMessage）
    GiftId    string  // 礼物ID（GiftMessage）
    GiftCount string  // 礼物数量（GiftMessage）
    GiftName  string  // 礼物名称（GiftMessage）
    MsgId     string  // 消息ID（用于幂等）
    AnchorId  string  // 主播ID
}
```

**关键字段映射**：

| 消息类型 | Type 字段 | 关键字段 |
|---------|-----------|---------|
| ChatMessage | 评论/弹幕 | Content=弹幕文本 |
| GiftMessage | 礼物 | GiftId/GiftCount/GiftName/Total |
| LikeMessage | 点赞 | Count=本批点赞数 |

const (

## 二、三平台Webhook接入对比实证

### 2.1 抖音（zBarrage_dy_api.go）

```go
// 抖音Webhook接入特点：
// 1. 签名验证：MD5(token + timestamp) 校验
// 2. 幂等处理：DyMsgIdCheck (滑动窗口去重，10000条)
//// 3. 消息分发：通过 zmgr_logic.go 的 convergeMessage() 路由
// 4. 初始化：zBarrage_dy_init.go 处理 Token 刷新和任务启动
```

- **消息类型**：ChatMessage / GiftMessage / LikeMessage / EnterMessage
- **协议**：JSON over HTTP POST
- **认证**：HMAC-SHA256 签名

### 2.2 快手（zBarrage_kuaishou_api.go）

```go
// 快手Webhook接入特点：
// 1. 无签名验证（基于IP白名单）
// 2. Push_type 路由：giftSend / liveComment / liveLike / follow
// 3. 统一转换为 pb.MessageList 结构
// 4. 返回 result=1 表示成功消费
```

**Push_type → Type 映射**：
```
giftSend    → "GiftMessage"   → pb.Message.GiftId/GiftTotalPrice
liveComment → "ChatMessage"  → pb.Message.Content
liveLike    → "LikeMessage"  → pb.Message.Count
follow      → (仅记录日志)
```

### 2.3 抖音 vs 快手 关键差异

| 维度 | 抖音 | 快手 |
|-----|------|------|
| 认证方式 | HMAC签名+Token | IP白名单 |
| 消息去重 | 内存Map(msgId滑动窗口) | unique_message_id |
| 点赞合并 | EnterMessage+LikeMessage分离 | liveLike合并推送 |
| 礼物字段 | GiftId+Count+TotalPrice | GiftId+Count+UnitPrice+TotalPrice |
| 主播标识 | author_open_id | author_open_id |
| 房间码 | room_id | room_code |

            continue

        pdb.LikeCount += likeCount

        // 3. 阈值Buff触发检查
        triggerLikeBuff(ws, msg.Uid, msg.Name, likeCount)

        // 5. 点赞特效（阈值触发才广播，避免刷屏）
        if shouldBroadcastLike(likeCount) {
            ws.WsSend(COMMAND_TIPS_S, &pb.TipsNotify{
                TipMsg: fmt.Sprintf("[%s] 点赞了 ×%s！", msg.Name, msg.Count),
                Type:   TipType_Like,
            })
        }
    }
}

## 四、游戏动作触发机制（关键缺口分析）

### 4.1 当前协议的限制

分析 `init_define.go` 发现：
- **没有独立的 GameFrame 命令**（COMMAND_GAME 相关未定义）
- 游戏帧广播依赖 `TipsNotify`（COMMAND_TIPS_S=4）
- UE4客户端接收 `TipsNotify` 后需要解析 TipMsg 内容

### 4.2 两种实现路径

**路径A：扩展 TipsNotify 协议（推荐，无损兼容）**

```go
// 利用现有 TipsNotify，Type 字段区分消息种类
ws.WsSend(COMMAND_TIPS_S, &pb.TipsNotify{
    TipMsg: "GAME_ACTION:attack:ou_xxx:玩家名:3",
    Type:   TipType_GameAction,
})
// UE4客户端解析 TipMsg 前缀，提取游戏动作
```

**路径B：新增 GameFrameNotify 协议（需要UE4配合）**

```protobuf
// 新增 protobuf
message GameFrameNotify {
    int32 FrameId = 1;
    repeated GameAction Actions = 2;
}
```
建议优先使用路径A，保持向后兼容。
