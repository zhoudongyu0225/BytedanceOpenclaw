## 一、项目部署现状分析

### 1.1 当前二进制部署模式

根据项目结构分析，当前项目采用**单二进制部署模式**：

```
commonDmGameServer/
├── dmGameServer.exe      # 弹幕服主程序
├── Server.exe            # 游戏逻辑服主程序
├── go.mod / go.sum       # Go依赖管理
├── dirConf.json          # 目录配置文件
└── generateJsons/        # 运行时配置（Gift.json, Buff.json等）
```

项目特点：
- **Go静态编译**：可生成单一可执行文件，天然适合容器化
- **去中心化设计**：无外部进程管理器，每个服务独立运行
- **配置外部化**：`dirConf.json`控制目录结构，`generateJsons/`存放游戏配置
- **协议工具链完整**：`toolpb/`、`toolProtoToPb/`、`toolDefineToProto/`等工具支持协议版本管理

### 1.2 现有运维脚本

```batch
工具启动服务器.bat      # 启动服务
工具关闭服务器.bat      # 停止服务
工具proto生成pb.bat     # 协议编译
工具协议生成proto.bat   # 协议生成
```

**问题识别**：
- 当前脚本为Windows批处理，无法直接用于生产Linux环境
- 缺少健康检查机制（`curl -f`或端口探测）
- 缺少优雅停止（graceful shutdown）处理
- 缺少滚动更新支持
- 日志管理依赖`zlog`包但未配置日志轮转

## 二、Docker容器化方案

### 2.1 多阶段构建Dockerfile（推荐）

```dockerfile
# ============ 构建阶段 ============
FROM golang:1.22-alpine AS builder

# 安装构建工具
RUN apk add --no-cache git make protoc

WORKDIR /app

# 依赖缓存
COPY go.mod go.sum ./
RUN go mod download

# 复制源码
COPY . .

# 协议编译（如果需要）
RUN protoc --go_out=. --go_opt=paths=source_relative pb/*.proto

# 编译弹幕服
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags="-s -w" -o dmGameServer .

# 编译游戏逻辑服
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -ldflags="-s -w" -o Server .

# ============ 运行阶段 ============
FROM alpine:3.19 AS runtime

# 安装运行时依赖
RUN apk add --no-cache tzdata ca-certificates curl

# 创建非root用户
RUN addgroup -g 1000 appgroup && \
    adduser -u 1000 -G appgroup -s /bin/sh -D appuser

WORKDIR /app

# 复制编译产物
COPY --from=builder /app/dmGameServer ./
COPY --from=builder /app/Server ./
COPY --from=builder /app/generateJsons/ ./generateJsons/
COPY --from=builder /app/dirConf.json ./

# 目录结构
RUN mkdir -p /app/logs /app/data && \
    chown -R appuser:appgroup /app

USER appuser

# 健康检查
HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
    CMD curl -f http://localhost:12011/health || exit 1

# 优雅停止（等待30秒让现有连接处理完毕）
STOPSIGNAL SIGTERM

ENTRYPOINT ["./dmGameServer"]
```

## 四、zerolog结构化日志增强

### 4.1 当前zlog包分析

根据`zlog/zlog.go`分析，项目使用`zerolog`进行日志记录。当前需要增强：

```go
// 当前代码中的日志调用示例
zlog.Logger.Info().Msgf("玩家评论   %v  %v %v %v ", msg.Uid, msg.Name, msg.Content, ws.AccountId)
zlog.Logger.Error().Msgf("UpdateTbgCache err:%v [%v]", err, key)
```

**问题**：
- 所有日志为消息字符串，无法结构化查询
- 缺少请求追踪ID（TraceID）
- 缺少日志轮转（log rotation）
- 生产环境需JSON格式以便ELK/Grafana Loki采集

### 4.2 增强后的zlog配置

```go
package zlog

import (
    "io"
    "os"
    "path/filepath"
    "time"

    "github.com/rs/zerolog"
    "github.com/rs/zerolog/pkgerrors"
    "gopkg.in/natefinn/lumberjack.v2"
)

func InitLogger(env string, logPath string, level string) {
    // JSON格式化 + 错误堆栈
    zerolog.ErrorStackMarshaler = pkgerrors.MarshalStack
    zerolog.TimeFieldFormat = time.RFC3339Nano

    var logLevel zerolog.Level
    switch level {
    case "debug":
        logLevel = zerolog.DebugLevel
    case "warn":
        logLevel = zerolog.WarnLevel
    case "error":
        logLevel = zerolog.ErrorLevel
    default:
        logLevel = zerolog.InfoLevel
    }
    zerolog.SetGlobalLevel(logLevel)

    if env == "production" {
        // Lumberjack日志轮转（每个文件最大100MB，保留30天，最多5个文件）
        writer := &lumberjack.Logger{
            Filename:   filepath.Join(logPath, "dmGameServer.log"),
            MaxSize:    100, // MB
            MaxAge:     30,  // 天
            MaxBackups: 5,
            Compress:   true,
            LocalTime:  true,
        }
        zerolog.Logger = zerolog.New(writer).
            With().
            Timestamp().
            Caller().
            Logger()
    } else {
        // 开发环境：控制台彩色输出
        zerolog.Logger = zerolog.New(os.Stdout).
            With().
            Timestamp().
            Caller().
            Logger().
            Output(zerolog.ConsoleWriter{Out: os.Stdout, TimeFormat: "15:04:05"})
    }
}
```

## 五、高可用架构设计

### 5.1 当前架构瓶颈分析

```
                    ┌─────────────┐
                    │   抖音      │
                    │ Webhook    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
```

### 5.3 Kafka多播消息路由（关键设计）

```go
// 弹幕服：接收平台消息并发布到Kafka
// zinit_mq.go 改造

type BarrageRouter struct {
    producer sarama.SyncProducer
}

func (r *BarrageRouter) Route(messageList *pb.MessageList) error {
    // 根据消息类型路由到不同topic
    topic := r.getTopic(messageList.Type)
    
    // 序列化为二进制（减小消息体）
    data, err := proto.Marshal(messageList)
    if err != nil {
        return err
    }
    
    msg := &sarama.ProducerMessage{
        Topic: topic,
        Key:   sarama.StringEncoder(messageList.AccountId), // 按主播分partition
        Value: sarama.ByteEncoder(data),
        Headers: []sarama.RecordHeader{
            {Key: []byte("msg_type"), Value: []byte(messageList.Type)},
            {Key: []byte("timestamp"), Value: []byte(fmt.Sprintf("%d", time.Now().Unix()))},
        },
    }
    
    _, _, err = r.producer.SendMessage(msg)
    return err
}

func (r *BarrageRouter) getTopic(msgType string) string {
    switch msgType {
    case "ChatMessage":
        return "barrage-chat"
    case "GiftMessage":
        return "barrage-gift"
    case "LikeMessage":
        return "barrage-like"
    default:
        return "barrage-unknown"
    }
}
```

```go
func (c *BarrageConsumer) ConsumeClaim(session sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for {
        select {
        case msg, ok := <-claim.Messages():
            if !ok {
                return nil
            }
            
            start := time.Now()
            var messageList pb.MessageList
            proto.Unmarshal(msg.Value, &messageList)
            
            // 处理消息
            switch messageList.Type {
            case "ChatMessage":
                ChatMessage(&messageList, nil) // 复用现有逻辑
            case "GiftMessage":
                GiftMessage(&messageList, nil)
            case "LikeMessage":
                LikeMessage(&messageList, nil)
            }
            
            // 记录消费进度（自动提交）
            session.MarkMessage(msg, "")
            
            // 记录指标
            metrics.BarrageMessagesTotal.WithLabelValues(messageList.Type, "").Inc()
            metrics.KafkaConsumeDuration.WithLabelValues(messageList.Type).Observe(time.Since(start).Seconds())
            
        case <-session.Context().Done():
            return nil
        }
    }
```

## 六、优雅停止与滚动更新

### 6.1 优雅停止（Graceful Shutdown）

当前`main.go`需要改造，添加信号处理和优雅停止：

```go
// main.go
package main

import (
    "context"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"

    "github.com/prometheus/client_golang/prometheus/promhttp"
    "github.com/rs/zerolog/log"
)

func main() {
    // 初始化服务
    InitServer()
    
    // 创建HTTP服务器（用于健康检查和指标）
    mux := http.NewServeMux()
    mux.HandleFunc("/health", healthHandler)
    mux.Handle("/metrics", promhttp.Handler())
    
    httpServer := &http.Server{
        Addr:    ":9090",
        Handler: mux,
    }
    
    go httpServer.ListenAndServe()
    
    // 等待中断信号
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    
    log.Info().Msg("收到停止信号，开始优雅关闭...")
    
    // 第一阶段：停止接收新连接
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    
    // 停止接收HTTP请求
    if err := httpServer.Shutdown(ctx); err != nil {
        log.Error().Err(err).Msg("HTTP服务关闭失败")
    }
    
    // 第二阶段：处理现有WebSocket连接
    if err := wsServer.GracefulShutdown(ctx); err != nil {
        log.Error().Err(err).Msg("WebSocket服务关闭失败")
    }
    
    // 第三阶段：关闭数据库连接
    if err := model.CloseMongoDB(ctx); err != nil {
        log.Error().Err(err).Msg("MongoDB连接关闭失败")
    }
    if err := model.CloseRedis(); err != nil {
        log.Error().Err(err).Msg("Redis连接关闭失败")
    }
    
    // 第四阶段：flush日志
    log.Info().Msg("服务已优雅停止")
}

func healthHandler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    w.Write([]byte(`{"status":"ok"}`))
}
```

| MongoDB写入慢 | 索引缺失/连接池满 | `db.currentOp()` |
| Kafka消费积压 | 消费者实例少/处理慢 | `kafka-consumer-groups.sh --describe` |
